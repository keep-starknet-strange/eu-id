## Decision
Your arithmetic is right on both counts, and it exposed a variable-conflation bug in
G0 §3 / WO-BL3 §3: **the "k = 64" starting point conflated ℓ (data symbols per row)
with k (RS message length / degree bound).** With that fixed, the notation and the v1
parameters are:

### 1. Notation
- `t` in `k > ℓ + t` **is** the opened-column count — same variable as the 180.
- The inequality is the per-row ZK condition: each row's codeword is the evaluation of
  a degree-`<k` polynomial carrying only `ℓ` data symbols; the remaining `k − ℓ`
  coefficients are drawn fresh at random, so any `t ≤ k − ℓ` revealed column
  evaluations are jointly uniform and leak nothing. It has nothing to do with
  proximity; it caps `t` from above given `k`, which is why `k = 64, t = 180` is
  unsatisfiable — as you observed.
- Your second observation is also correct: at `n = 256`, `e < (n−k)/2` caps
  `(1 − e/n)` too far from 0 for any `t` to reach 2^-128 while respecting ZK. The
  codeword length must grow. Longfellow's rate-1/7 + t=132 numbers rely on their
  Appendix-C *improved* analysis; v1 uses the conservative Thm-4-style bound below,
  so our `t` is higher. Adopting the Appendix-C analysis later to cut `t` (proof
  size) is a v2 optimization, not a v1 requirement.

### 2. Pinned v1 parameters (normative for BL3 §3-RESULT)
```
ℓ = 64     (data symbols per row; m = ⌈total_values / 64⌉ rows)
t = 200    (opened columns)
k = 264    (= ℓ + t, ZK-tight)
n = N = 1024   (codeword length; rate k/n ≈ 1/3.9)
e = 379    (proximity radius used in the bound)
```
Constraint check: `e < (n−k)/2 = 380` ✓; `n > 2k + e` (1024 > 907) ✓;
`k ≥ ℓ + t` (264 = 64+200) ✓; `|F| ≥ ℓ + n` trivially ✓.

Soundness terms:
- `(1 − e/n)^t = (0.62988)^200 ≈ 2^-133.4`
- `(2k/n)^t = (0.515625)^200 ≈ 2^-191`
- `((k+ℓ)/n)^t = (0.3203)^200 ≈ 2^-328`
- `(n+3)/|F| ≈ 2^-246`
Sum ≈ **2^-133 ≤ 2^-128** ✓.

### 3. What the code must assert before BL3 is accepted
In a `#[test]` (f64 log2 arithmetic is fine) plus debug asserts in the builder:
1. `k >= l + t`
2. `e < (n - k) / 2`
3. `n > 2 * k + e`
4. recompute the four bound terms from the actual `(n, k, l, t, e)` constants and
   assert the sum ≤ 2^-128 — parameters change only by re-running this computation.
Copy the §2 numbers into WO-BL3's §3-RESULT block; consider this the architect ack
of that block once the test exists and passes.

### 4. Honest consequences (record in perf-log, do not silently absorb)
- **Proof size grows:** t·m·32 B + Merkle paths. With witness ≈ 2,680 (LAYOUT v2,
  answers/Q-022.md) + OTP pad rows, m ≈ 45–90 ⇒ **roughly 350–620 KB**
  pre-optimization, superseding G0's ~230 KB estimate. Record the real number.
- **Encode cost grows:** naive Lagrange is m·O(n·k) ≈ 10–25 M mults ≈ 250–600 ms at
  25 ns — G0's "naive fine" claim was for k=64/N=256 and does NOT survive these
  parameters. Use barycentric weights (precompute once, O(k) per eval point) and
  measure; if row encoding still dominates the G2 budget, mailbox with numbers —
  quasi-linear multipoint evaluation (subproduct trees) is the sanctioned fallback,
  smaller `t` via Appendix-C analysis the one after.

Keep RS encoding + Merkle openings as implemented; only the parameter constants and
the §3-RESULT computation change.
