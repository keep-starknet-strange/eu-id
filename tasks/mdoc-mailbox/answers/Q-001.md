## Decision
Take SHA option 1 + P256 option 1 for Phase 0b and move to Phase A — after a
bounded (≤30 min) measurement, and with one small guard test added now. Both
refactors are legitimate but neither is Phase-0b scope; if the measurement
shows the waste is large, they become their own scoped tasks that run parallel
to Phase A, not gates on it.

## Why your trials failed (confirming your diagnosis, one level deeper)
Both failures are the same bug class: **the preprocessed-ID contract is
"ID uniquely determines content", and both trials violated it.** Global dedup
keyed those IDs across instances; the moment two instances disagree on content
(size-dependent `is_first`/round-cyclic columns for SHA, witness-dependent
hinted-mul schedules for P256), one instance's constraints are evaluated
against the other's column. `ConstraintsNotSatisfied` is the expected symptom,
not a mystery. Your "likely cause" sections are correct.

## Required now (Phase 0b, ships with option 1 + option 1)
Add the invariant guard test: at combined-proof assembly, hash every
preprocessed column and assert that equal IDs ⇒ equal content, panicking with
both component names and the ID. Cost: ~an hour. It converts this entire bug
class from a silent prove-time constraint failure into a named error at trace
build, and it would have caught both of your trials immediately. Every future
sizing/dedup experiment gets cheaper.

## Required now (the measurement)
Before accepting the waste, price it — analytically, no refactor:
1. Print the four natural logs and `shared_sha_log` for the standard fixture.
2. Per padded instance, waste ≈ (per-row cells of that SHA module, from
   shape_dump: module cells ÷ 2^log) × (2^shared − 2^natural). Static lookup
   tables dedupe regardless — count only main-trace + interaction columns.
3. Same arithmetic for the P256 namespace: total cells of preprocessed columns
   duplicated under `mdoc/device` that are content-identical to the issuer's
   (deterministic tables only; schedules are genuinely different).
Record both numbers in the answer thread / STATUS.

Decision rule: if the combined waste is **< 1.0 M cells**, option 1 + option 1
stands and the refactors stay parked (for scale: the WO-3.2a 163 k-cell merge
was measurement noise; the 1.3 M-cell merges bought ~1.5–4 %). If **≥ 1.0 M**,
file the refactor(s) as separate tasks with the scoping below — and still
start Phase A now.

## Scoping for the eventual refactors (recorded so nobody re-derives)
- **SHA option 2** (correct fix): put `log_n_rows` into the IDs of
  size-dependent preprocessed columns ONLY (`is_first`, round-cyclic/schedule
  columns); static table IDs unchanged so they keep deduping globally. Touches
  ID generation, verifier layout derivation, and the guard test proves the
  result. Medium, bounded.
- **P256 option 2**: audit P256 preprocessed IDs into deterministic
  (range13/range9/signed-carry value+active tables, selector tables,
  deterministic prepared-point limb tables — shared IDs, no namespace) vs
  witness-dependent (hinted-mul schedule columns — keep per-instance
  namespace). Namespace only the latter. The guard test again proves it.
- **P256 option 3 is rejected.** Forcing identical issuer/device schedules
  changes hinting assumptions blind; nobody has analyzed completeness of a
  shared schedule across two independent signatures. Do not pursue without a
  dedicated analysis note.
- **SHA option 3** (multi-message module) is out of scope entirely; it only
  makes sense inside a future SHA restructure (GKR-era), not as a sizing fix.

## One forward-looking constraint
A static preprocessed-tree cache + verifier-pinned tree-0 root is on the main
roadmap. Both refactors above change preprocessed layout/IDs and therefore the
pinned root. Land them (if the measurement justifies them) BEFORE any root
constant is baked, or budget a root re-pin in the same change.
